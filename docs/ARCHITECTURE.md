# Architecture and operational policy

`apps/web` contains React feature modules for auth, leagues, rooms/lobby, auction, squads, settings, chat and voice. Router access requires identity. Refresh restores auth and subscribes to an authoritative room snapshot; room status selects lobby/auction/results. TanStack Query owns HTTP catalog/list/squad requests. Zustand owns the socket snapshot and presentation preferences. Saved squads and lineup edits have ownership-checked HTTP endpoints independent of live room membership; even a removed owner retains their purchased squad after completion. Authenticated query caches are keyed by user ID. Local countdowns use the persisted absolute deadline plus server-time offset. React Hook Form/Zod validates room creation; the server independently validates every operation. Shared shadcn-style Button uses Radix Slot/CVA; the player-directory dialog uses Radix focus trapping and Escape support. Responsive CSS tokens, reduced motion, safe-area padding and disabled controls cover device preferences and connection state.

`packages/shared` defines types, Zod command envelopes, eligibility and integer money rules. `apps/server` separates auth, dataset adaptation, persistence, room admission and the auction engine. A managed frontend Socket.IO client has typed events and acknowledgements. Room voice uses a separate authenticated signalling namespace and browser WebRTC, bound to the active auction socket session. Optional LiveKit carries media when configured; its private signing keys stay on the backend. Voice lifecycle and setup are documented in `VOICE.md`.

## Mutation/persistence model

One backend instance is supported. In development an atomic-file repository serializes all mutations, clones before editing and changes in-memory state only after successful persistence. `.runtime` holds the durable local state. It is refused in production. Postgres uses a transaction with `SELECT ... FOR UPDATE` on the room row and database constraints for unique room code, owner/team, room/player purchase and lot purchase. The persisted aggregate contains the complete restartable state. Normalized membership/lot/bid/purchase/block/chat/lineup ledgers are written in the same transaction. RLS denies all browser access to room data; the membership-checking API is the access boundary. Seeds populate normalized catalog tables.

Commands carry UUID request ID, room ID, expected version and lot ID when relevant. Commands are accepted only from the verified owner's active connected session. Retries with the same ID are no-ops after membership/session validation. Concurrent commands using the same version cause one to succeed and the other to receive a stale-version error and refreshed snapshot. The client asks the user to review and retry instead of automatically placing a later bid. Current bid amounts come exclusively from server rules. Persistence failure rolls back and returns an error; no success event is broadcast.

Accepted bids reset `endsAt`. Highest bidder cannot bid or pass. Pass is irreversible for one lot. Full squads, insufficient budgets, overseas caps and optional minimum base-price budget reservation are checked on the server. The reservation rule uses the dataset's minimum base price times remaining empty slots; it is a floor and does not guarantee that every remaining slot can be filled at future auction prices. Temporarily disconnected challengers retain eligibility for early-sale calculation. A disconnection alone never counts as a pass. Kicked/left/frozen teams are ineligible for new bids, while an accepted highest bid remains binding.

## State and recovery

Lobby → running → reveal → next running lot; paused, unsold_decision, completed and cancelled are explicit persisted states. Sale resolution runs synchronously within a locked repository mutation: confirm unresolved lot, insert purchase, deduct budget, persist sold result and set a 2.5-second reveal deadline. The scheduler checks due persisted state every 250ms; it never trusts a client timer. JavaScript event-loop processing is serial in the first instance, with Postgres row locking as the persistent guard. An unsold rerun creates fresh lot UUIDs. Completion happens when the queue/unsold pool is exhausted or no active owner can afford/fit any remaining player. Only the host decides rerun/finish when unsold acquisitions remain possible. There is no subjective team winner.

At startup, old socket sessions are cleared and connected owners become disconnected, preserving prior already-disconnected deadlines. Expired unresolved lots are resolved exactly once, including accepted bids whose deadline passed during downtime. Expired reveal intervals advance from persisted state. An exception aborts startup or the transaction and logs the failure instead of guessing. No client independently advances the queue. The server-time snapshot includes the latest reveal state; celebration effects are suppressed on restored resolved lots.

Disconnected lobby seats are reserved for two minutes, then released. During auctions team ownership and purchases remain; no new owner takes over automatically. Explicit pre-start leave releases the seat immediately. During-auction leave freezes bidding for that owner but preserves accepted bids and purchases; the same owner may authenticate and return unless blocked. Host disconnect preserves authority for two minutes, then the earliest connected eligible owner succeeds. If nobody is connected the running auction pauses, and an eligible returning owner can become host. No background voice is promised.

Newest authenticated socket subscription controls the team. Older sessions receive a takeover notice and lose room socket membership; only the active session may mutate. Each reconnect sends a complete sanitized snapshot. Kicks persist room blocks, evict sockets, remove voice participation and preserve already purchased players. Account IDs come from Auth, never client IDs or socket IDs. Socket IDs are ephemeral control-session identifiers only. Passwords use salted scrypt; join/auth endpoints and chat are rate-limited. Chat is plain text, capped at 500 characters/message, deduplicated via command IDs, retained to 1,000 messages per room, and paginated 50 at a time. UI history loading preserves scroll intent and offers an unread/latest control.

## Scaling and limits

Do not run multiple backend instances with the file adapter. Postgres protects individual writes, but schedulers, socket fanout, voice cleanup and presence still assume one instance. Horizontal scaling requires shared coordination/leadership plus a compatible Socket.IO adapter; Redis/microservices/Kubernetes were intentionally not introduced.

HTTP catalog imports/SQL migration and Supabase/LiveKit integration are implemented, but full hosted Auth auction acceptance, LiveKit quotas/revocation and real mobile voice require further acceptance testing. The local browser suite exercises development Auth and file persistence; rollback-only Postgres checks additionally verify ledger writes, trade custody and transaction rollback against the configured database. App shell offline caching does not enable offline bidding. Global HTTP limits are process-local. There is no scoring model, custom increment ladder, full profile/avatar uploader, or account recovery UI yet. Fixed integer increments are configurable before start. The room creation form has all settings; lobby edits expose timer/voice plus team changes, while the server supports the remaining allowed settings through validated commands.

## Audio and trading

Personal audio follows confirmed snapshots and server-relative deadlines. Device preferences select countdown, results, spoken voice and volume. Restored lots are primed silently, and inactive/hidden sessions suppress audio. Web Audio effects and device speech synthesis run independently of voice chat and cannot place bids or resolve lots.

Trade proposals and responses use membership-checked HTTP endpoints and the same locked repository mutation as auction commands. Sending establishes the sender's agreement; only the recipient accepts. Acceptance atomically moves purchase custody and credits after rechecking current ownership, roster limits, reserve and standing-bid commitments. Proposal IDs and resolved responses are idempotent. Offers remain private to their two owners and expire after 24 hours. A read-only authenticated `/trades` namespace invalidates saved-squad/trade queries without taking over the auction session; live roster rendering follows auction snapshots. Room JSONB stores the bounded offer ledger, while normalized purchase membership updates in the same SQL transaction. See [audio and trade policy](AUDIO-TRADES.md).
